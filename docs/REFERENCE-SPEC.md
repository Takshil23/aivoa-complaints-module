### The three mandatory AI tools

| # | Tool | Narration requirement |

## 1. Layout

Single full-viewport screen. **No global nav, no sidebar, no header, no footer** other than the copilot's own
byline. Two panes, vertical divider at ~60% width.

```
┌──────────────────────────────────────────────┬────────────────────────────────┐
│  LEFT  (~60%)  scrollable form               │  RIGHT (~40%)  chat, fixed     │
│                                              │                                │
│  Log Customer Complaint          [ status ]  │  ⚗ AIVOA Copilot          ●    │
│  API & FDF Quality Assurance Module          │  Drop complaint files or       │
│  ─────────────────────────────────────────   │  paste text below.             │
│                                              │  ┌───────────────────────────┐ │
│  1. …section…                                │  │ scrollable message list   │ │
│  2. …section…                                │  │                           │ │
│  3. …section…                                │  └───────────────────────────┘ │
│  4. …section…                                │  [📎  Type a message…    ✓ ]  │
│  ┌────────────────────────────────────────┐  │      POWERED BY LANGGRAPH      │
│  │  AI copilot risk assessment  (tinted)  │  │                                │
│  └────────────────────────────────────────┘  │                                │
```

- Left pane scrolls independently; right pane is fixed height with its own scrolling message list.
- Form fields are laid out in a **2-column grid**; full-width for textareas and Complaint Category.

## 2. Left pane — Log Customer Complaint

### Header
- Title: **Log Customer Complaint** (large, bold, near-black)
- Subtitle: **API & FDF Quality Assurance Module** (grey)
- Right-aligned **status pill**:
  - Empty state → `Pending Triage` — amber/yellow pill, amber text, no dot
  - After successful parse → `● Ready to Commit` — mint-green pill, dark green text, leading green dot
- Thin horizontal rule under the header.

### Section numbering is DYNAMIC
The section list itself changes once the agent has parsed a complaint. This is not a cosmetic detail — it means
**the agent returns the form schema, not just values.**

**Empty state (3 sections):**
| # | Section | Fields |
|---|---------|--------|
| 1 | PRODUCT & BATCH IDENTIFICATION | `Product Name (API/FDF)` → placeholder *"Awaiting AI extraction…"*; `Batch / Lot Number` → *"Awaiting AI extraction…"* |
| 2 | FACILITY & MATERIAL IMPACT | `Originating Site Block` → **select**, placeholder *"Awaiting AI classification…"*; `Impacted Non-Product Materials (NPM)` → *"e.g., Primary packaging…"* |
| 3 | DEFECT ANALYSIS | `Structured Defect Summary` → **textarea**, *"AI will synthesize the complaint into a formal QMS description…"* |

**Populated state (4 sections):**
| # | Section | Fields |
|---|---------|--------|
| 1 | ORIGIN & CUSTOMER DETAILS | `Complaint Source`, `Customer Name` |
| 2 | PRODUCT & BATCH IDENTIFICATION | `Product Name`, `Product Strength` *(label becomes `Product Strength/Grade` for an API)*, `Batch / Lot Number`, `Affected Quantity`, `Manufacturing Date`, `Expiry Date` |
| 3 | FACILITY & MATERIAL IMPACT | `Originating Site Block` (**select**), `Impacted Non-Product Materials (NPM)` |
| 4 | DEFECT ANALYSIS | `Complaint Category`, `Complaint Description` (**textarea**, ~3 rows) |

Note the label drift: `Product Name (API/FDF)` → `Product Name`, and `Product Strength` →
`Product Strength/Grade` when the product is an API rather than a finished dose form. Field **labels are
part of the agent's output.**

### AI copilot risk assessment panel
Visually distinct: pale indigo/lavender fill, subtle border, rounded, generous padding. Header row =
shield-check icon + label **"AI copilot risk assessment"**. All labels inside the panel are indigo (not grey
like the rest of the form).

| Field | Type | Layout |
|-------|------|--------|
| `Severity (Suggested)` | text | left half |
| `Suggested Next Action` | text | right half |
| `Initial Risk Assessment` | text (long, overflows) | full width |

### Primary action
Full-width solid indigo button: **`Commit to QMS Ledger`**.
⚠️ **Never clicked in the demo** — post-commit behaviour is unspecified. See §7.

**Resulting form state:**
| Field | Value |
|-------|-------|

| Customer Name | `Apollo Pharmacy` |
| Product Name | `Amoxicillin Capsules` |
| Product Strength | `500 mg` |
| Batch / Lot Number | `AMX240602` |
| Affected Quantity | `12 capsules` |
| Manufacturing Date | `March 2026` |

| Originating Site Block | `Manufacturing` |
| Impacted NPM | `Primary Packaging (Bottle)` |

**Inference worth noting:** `Affected Quantity: 12 capsules`, `Complaint Source: Pharmacy`,

also not in the input. So the reference implementation lets the model invent plausible QMS detail. Decide
deliberately whether you replicate that or mark inferred values (see §7).

## 6. Behaviour checklist (what a reviewer will test)

- [ ] Paste raw complaint text → form + risk assessment populate; status → Ready to Commit
- [ ] Form is populated **only** via the copilot
- [ ] Natural-language edit patches **only** named fields; all others preserved
- [ ] Edit also re-evaluates the risk assessment (narration explicitly requires this)
- [ ] Typos and malformed input ("capcules", "260712Aand") handled gracefully
- [ ] PDF upload → OCR progress card → extraction → form + risk assessment populate
- [ ] Extracted complaint is then editable by natural language
- [ ] Missing data surfaces as `Not Provided`, not blank
- [ ] Field labels adapt to product type (API vs FDF)
- [ ] Assistant confirmation names the changed fields and quotes new values
- [ ] Idle/working/success state dot + status pill stay in sync
- [ ] Attachment card renders filename + type

## 8. Suggested architecture (pending stack confirmation)

Agent-returns-schema is the key design decision. A single LangGraph agent exposing three tools, each
returning a **form patch**, with the UI rendering whatever schema arrives.

```
POST /api/chat          { session_id, message }        → SSE/stream: tokens + form_patch events
POST /api/upload        multipart PDF                  → stream: progress stages + form_patch
GET  /api/session/:id                                  → current form state + transcript
POST /api/complaints    commit                         → { complaint_id: "CC-2026-00155" }
```

**Agent state**
```
{
  session_id,
  messages: [...],
  form_schema: { sections: [ { index, title, fields: [ { key, label, type, value, options?, inferred? } ] } ] },
  risk_assessment: { severity, suggested_next_action, initial_risk_assessment },
  status: "pending_triage" | "ready_to_commit"
}
```

**Tools**
- `log_complaint(raw_text)` → full schema + values + risk assessment
- `edit_complaint(instruction)` → sparse patch `[{ field_key, new_value }]` + refreshed risk assessment;
  merge over existing state so untouched fields survive
- `extract_document(file)` → parse PDF → same shape as `log_complaint`, emitting progress events

Keeping `edit_complaint` a **sparse patch** (not a full re-generation) is what makes "preserving all other
complaint information" reliable.
